MEGASPORT - DOCUMENTACION DE LA BASE DE DATOS
================================================
Fecha de esta documentacion: 2026-10-03
Proyecto: MegaSport - Tienda virtual de ropa y calzado deportivo
Motor: PostgreSQL
Proveedor actual: Supabase
Estado: Base de datos creada, poblada con datos iniciales y conectada al backend real


1. OBJETIVO GENERAL
-------------------

La base de datos de MegaSport almacena la informacion persistente necesaria
para la tienda virtual.

Actualmente ya existen las tablas principales definidas por el modelo
entidad-relacion aprobado y ya se insertaron los datos iniciales de catalogo,
couriers, proveedores de tarjeta y usuarios de prueba.

La base ya esta conectada con el proyecto real.

Flujo actual:

Frontend React
    -> HTTP
    -> Backend Node.js + Express
    -> pg / Pool
    -> PostgreSQL en Supabase

IMPORTANTE:
El frontend NO se conecta directamente a PostgreSQL.

La conexion privada con la base existe solamente en el backend mediante la
variable de entorno DATABASE_URL.


2. CONEXION ACTUAL CON EL PROYECTO
----------------------------------

El backend se encuentra en:

megasport-backend/

La cadena privada de conexion se almacena en:

megasport-backend/.env

Variables principales:

PORT=3000
DATABASE_URL=...

PORT=3000 corresponde al servidor Express, NO al puerto de PostgreSQL.

PostgreSQL utiliza el puerto 5432 dentro de la cadena de conexion.

La conexion inicial mediante "Direct connection" de Supabase produjo problemas
de conectividad en la red de desarrollo debido al uso de IPv6.

La configuracion funcional actual utiliza:

- Supabase
- Connection Method: Session pooler
- Type: URI
- PostgreSQL
- pg desde Node.js

La cadena exacta contiene credenciales privadas y no debe incluirse en esta
documentacion ni subirse al repositorio.

El archivo:

src/config/database.ts

crea un Pool de conexiones de pg.

Conceptualmente:

new Pool({
    connectionString: process.env.DATABASE_URL,
    ssl: {
        rejectUnauthorized: false
    }
})

Los servicios del backend ejecutan SQL usando:

pool.query(...)


3. MODULO QUE YA USA LA BASE REAL
---------------------------------

Actualmente el modulo de catalogo ya trabaja con datos reales.

Endpoints implementados:

GET /api/categorias
GET /api/productos
GET /api/productos?categoria=hombre
GET /api/productos/:id

Las paginas del frontend que ya consumen estos datos son:

- Home

Estas paginas ya reciben de PostgreSQL:

- Categorias

Por lo tanto, para esta parte del sistema ya existe el flujo completo:

React -> Express -> PostgreSQL -> Express -> React


4. TABLAS ACTUALES
------------------

Actualmente existen 10 tablas principales:

1. tarjeta
2. courier
3. usuario
4. categoria
5. producto
6. variante_producto
7. carrito
8. articulo_en_carrito
9. orden
10. detalle_orden

Las tablas fueron creadas con PostgreSQL usando los siguientes scripts.


5. SCRIPT REAL DE CREACION DE TABLAS
------------------------------------

CREATE TABLE tarjeta (
    identificador VARCHAR(15) NOT NULL,
    activo BOOLEAN NOT NULL DEFAULT TRUE,
    nombre VARCHAR(50) NOT NULL UNIQUE,
    host VARCHAR(45) NOT NULL,
    script_de_autorizacion VARCHAR(255) NOT NULL,
    PRIMARY KEY (identificador)
);

CREATE TABLE courier (
    identificador VARCHAR(15) NOT NULL,
    activo BOOLEAN NOT NULL DEFAULT TRUE,
    nombre VARCHAR(100) NOT NULL UNIQUE,
    host VARCHAR(45) NOT NULL,
    script_de_consulta VARCHAR(255) NOT NULL,
    script_de_envio VARCHAR(255) NOT NULL,
    script_de_status VARCHAR(255) NOT NULL,
    PRIMARY KEY (identificador)
);

CREATE TABLE usuario (
    id INT GENERATED BY DEFAULT AS IDENTITY NOT NULL,
    hash_contrasena VARCHAR(255) NOT NULL,
    rol VARCHAR(20) NOT NULL,
    direccion VARCHAR(300) NOT NULL,
    codigo_de_destino CHAR(5) NOT NULL,
    telefono VARCHAR(25) NOT NULL,
    creado_en TIMESTAMP(0) WITHOUT TIME ZONE NOT NULL DEFAULT NOW(),
    nombre VARCHAR(150) NOT NULL,
    email VARCHAR(254) NOT NULL UNIQUE,
    PRIMARY KEY (id),
    CHECK (rol IN ('ADMINISTRADOR', 'CLIENTE'))
);

CREATE TABLE categoria (
    id INT GENERATED BY DEFAULT AS IDENTITY NOT NULL,
    nombre VARCHAR(100) NOT NULL UNIQUE,
    PRIMARY KEY (id)
);

CREATE TABLE producto (
    id INT GENERATED BY DEFAULT AS IDENTITY NOT NULL,
    id_categoria INT NOT NULL,
    url_img VARCHAR(500) NULL,
    activo BOOLEAN NOT NULL DEFAULT TRUE,
    creado_en TIMESTAMP(0) WITHOUT TIME ZONE NOT NULL DEFAULT NOW(),
    nombre VARCHAR(150) NOT NULL,
    descripcion VARCHAR(1000) NULL,
    precio DECIMAL(10,2) NOT NULL,
    PRIMARY KEY (id),
    FOREIGN KEY (id_categoria) REFERENCES Categoria(id), 
    CHECK (precio >= 0)
);

CREATE TABLE variante_producto (
    id_variante INT GENERATED BY DEFAULT AS IDENTITY NOT NULL,
    id_producto INT NOT NULL,
    talla VARCHAR(20) NOT NULL,
    activo BOOLEAN NOT NULL DEFAULT TRUE,
    sku VARCHAR(50) NOT NULL UNIQUE,
    stock INT NOT NULL DEFAULT 0,
    stock_minimo INT NOT NULL DEFAULT 0,
    color VARCHAR(50) NOT NULL,
    PRIMARY KEY (id_variante),
    FOREIGN KEY (id_producto) REFERENCES producto(id),
    CONSTRAINT unico_varianteProducto_combinacion UNIQUE (id_producto, talla, color),
    CHECK (stock >= 0),
    CHECK (stock_minimo >= 0)
);

CREATE TABLE carrito (
    id INT GENERATED BY DEFAULT AS IDENTITY NOT NULL,
    id_usuario INT NOT NULL,
    creado_en TIMESTAMP(0) WITHOUT TIME ZONE NOT NULL DEFAULT NOW(),
    PRIMARY KEY (id),
    FOREIGN KEY (id_usuario) REFERENCES usuario(id)
);

CREATE TABLE articulo_en_carrito (
    id_item INT GENERATED BY DEFAULT AS IDENTITY NOT NULL,
    id_carrito INT NOT NULL,
    id_variante INT NOT NULL,
    cantidad INT NOT NULL,
    PRIMARY KEY (id_item),
    FOREIGN KEY (id_carrito) REFERENCES carrito(id),
    FOREIGN KEY (id_variante) REFERENCES variante_producto(id_variante),
    CHECK (cantidad > 0),
    CONSTRAINT unico_articuloCarrito_variante UNIQUE (id_carrito, id_variante)
);

CREATE TABLE orden (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY NOT NULL,
    id_usuario INT NOT NULL,
    id_tarjeta VARCHAR(15) NOT NULL,
    id_courier VARCHAR(15) NOT NULL,
    creado_en TIMESTAMP(0) WITHOUT TIME ZONE NOT NULL DEFAULT NOW(),
    fecha_hora TIMESTAMP(0) WITHOUT TIME ZONE NOT NULL DEFAULT NOW(),
    subtotal_antes_de_envio DECIMAL(10,2) NOT NULL,
    costo_envio DECIMAL(10,2) NOT NULL,
    total DECIMAL(10,2) NOT NULL,
    codigo_del_destino CHAR(5) NOT NULL,
    direccion_de_envio VARCHAR(300) NOT NULL,
    estado_de_pagado VARCHAR(10) NOT NULL,
    num_autorizacion VARCHAR(100) NOT NULL,
    num_envio VARCHAR(100) NOT NULL,
    estado_envio SMALLINT NOT NULL DEFAULT 1,
    PRIMARY KEY (id),
    FOREIGN KEY (id_usuario) REFERENCES usuario(id),
    FOREIGN KEY (id_tarjeta) REFERENCES tarjeta(identificador),
    FOREIGN KEY (id_courier) REFERENCES courier(identificador),
    CHECK (subtotal_antes_de_envio >= 0),
    CHECK (costo_envio >= 0),
    CHECK (total = subtotal_antes_de_envio + costo_envio),
    CHECK (estado_de_pagado IN ('APROBADO','DENEGADO')),
    CHECK (estado_envio BETWEEN 1 AND 5)
);

CREATE TABLE detalle_orden (
    id INT GENERATED BY DEFAULT AS IDENTITY NOT NULL,
    id_orden BIGINT NOT NULL,
    id_variante INT NOT NULL,
    precio_por_unidad DECIMAL(10,2) NOT NULL,
    cantidad_de_articulos INT NOT NULL,
    PRIMARY KEY (id),
    FOREIGN KEY (id_orden) REFERENCES orden(id),
    FOREIGN KEY (id_variante) REFERENCES variante_producto(id_variante),
    CHECK (precio_por_unidad >= 0),
    CHECK (cantidad_de_articulos > 0),
    CONSTRAINT unico_detalleOrden_variante UNIQUE (id_orden,id_variante)
);


6. EXPLICACION DE CADA TABLA
----------------------------

6.1 tarjeta
-----------

Representa a cada proveedor externo de tarjetas.

Clave primaria:
- identificador VARCHAR(15)

Campos:
- identificador
- activo
- nombre
- host
- script_de_autorizacion

Uso futuro:
El backend identificara el emisor de la tarjeta, consultara esta tabla y
construira la llamada al Web Service correspondiente usando host +
script_de_autorizacion.

IMPORTANTE:
Los hosts actuales son temporales/de prueba.
Todavia deben reemplazarse por las IP/hosts reales entregados por los grupos
responsables de los proveedores de tarjeta.


6.2 courier
-----------

Representa a cada empresa externa de envios.

Clave primaria:
- identificador VARCHAR(15)

Campos:
- identificador
- activo
- nombre
- host
- script_de_consulta
- script_de_envio
- script_de_status

Uso futuro:
El backend consultara esta tabla para construir las llamadas de:
- consulta de cobertura/costo
- solicitud de envio
- consulta de estado

IMPORTANTE:
Los hosts actuales son temporales/de prueba.
Todavia deben reemplazarse por los hosts/IP reales de cada grupo de Courier.


6.3 usuario
-----------

Representa clientes y administradores.

Clave primaria:
- id generado automaticamente mediante IDENTITY

Campos:
- id
- hash_contrasena
- rol
- direccion
- codigo_de_destino
- telefono
- creado_en
- nombre
- email

Restriccion de rol:

CHECK (rol IN ('ADMINISTRADOR', 'CLIENTE'))

email es UNIQUE.

IMPORTANTE SOBRE CONTRASENAS:
Los usuarios iniciales tienen actualmente:

PENDIENTE_HASH_BACKEND

en hash_contrasena.

Esto NO es una contraseña real ni un hash terminado.

La implementacion pendiente del backend debera:
- recibir la contraseña del usuario
- generar un hash seguro
- guardar solamente el hash
- comparar hashes durante login

Las contraseñas nunca deben guardarse en texto plano.


6.4 categoria
-------------

Representa las categorias del catalogo.

Clave primaria:
- id IDENTITY

Campo principal:
- nombre UNIQUE


6.5 producto
------------

Representa el producto general.

Clave primaria:
- id IDENTITY

Clave foranea:
- id_categoria -> categoria(id)

Campos:
- id
- id_categoria
- url_img
- activo
- creado_en
- nombre
- descripcion
- precio

Regla importante:
El precio vive en producto, no en variante_producto.

Todas las variantes de un mismo producto comparten el mismo precio.

Restriccion:

CHECK (precio >= 0)


6.6 variante_producto
---------------------

Representa una combinacion concreta de producto, talla y color.

Clave primaria:
- id_variante IDENTITY

Clave foranea:
- id_producto -> producto(id)

Campos:
- id_variante
- id_producto
- talla
- activo
- sku
- stock
- stock_minimo
- color

sku es UNIQUE.

Tambien existe:

UNIQUE (id_producto, talla, color)

Esto evita repetir la misma combinacion de producto+talla+color.

Restricciones:
- stock >= 0
- stock_minimo >= 0


6.7 carrito
-----------

Representa un carrito asociado a un usuario.

Clave primaria:
- id

Clave foranea:
- id_usuario -> usuario(id)

Campos:
- id
- id_usuario
- creado_en

Actualmente todavia no se han insertado carritos reales desde el backend.


6.8 articulo_en_carrito
-----------------------

Representa cada variante guardada dentro de un carrito.

Clave primaria:
- id_item

Claves foraneas:
- id_carrito -> carrito(id)
- id_variante -> variante_producto(id_variante)

Campos:
- id_item
- id_carrito
- id_variante
- cantidad

Restriccion:
- cantidad > 0

UNIQUE (id_carrito, id_variante)

evita que una misma variante aparezca duplicada como filas separadas dentro
del mismo carrito.

Actualmente esta tabla no contiene datos iniciales.


6.9 orden
---------

Representa una compra formalizada.

Clave primaria:
- id BIGINT IDENTITY

Claves foraneas:
- id_usuario -> usuario(id)
- id_tarjeta -> tarjeta(identificador)
- id_courier -> courier(identificador)

Campos principales:
- creado_en
- fecha_hora
- subtotal_antes_de_envio
- costo_envio
- total
- codigo_del_destino
- direccion_de_envio
- estado_de_pagado
- num_autorizacion
- num_envio
- estado_envio

Restricciones:

subtotal_antes_de_envio >= 0
costo_envio >= 0
total = subtotal_antes_de_envio + costo_envio
estado_de_pagado IN ('APROBADO','DENEGADO')
estado_envio BETWEEN 1 AND 5

Estados de envio previstos:
1 = Orden nueva
2 = Surtiendose
3 = Empacandose
4 = En ruta
5 = Entregada

Actualmente no existen ordenes iniciales insertadas.
Las ordenes deberan ser creadas por el backend durante el flujo real de compra.


6.10 detalle_orden
------------------

Representa cada variante comprada dentro de una orden.

Clave primaria:
- id

Claves foraneas:
- id_orden -> orden(id)
- id_variante -> variante_producto(id_variante)

Campos:
- id
- id_orden
- id_variante
- precio_por_unidad
- cantidad_de_articulos

precio_por_unidad se guarda como una copia historica del precio usado en el
momento de la compra.

Esto permite conservar el precio original aunque producto.precio cambie en el
futuro.

Restricciones:
- precio_por_unidad >= 0
- cantidad_de_articulos > 0
- UNIQUE (id_orden, id_variante)

Actualmente no existen detalles iniciales.


7. RELACIONES PRINCIPALES
-------------------------

Categoria 1 ---- N Producto

Producto 1 ---- N Variante_producto

Usuario 1 ---- N Carrito

Carrito 1 ---- N articulo_en_carrito

Variante_producto 1 ---- N articulo_en_carrito

Usuario 1 ---- N Orden

Tarjeta 1 ---- N Orden

Courier 1 ---- N Orden

Orden 1 ---- N detalle_orden

Variante_producto 1 ---- N detalle_orden

16. INTEGRIDAD Y REGLAS IMPORTANTES
-----------------------------------

La base ya implementa varias reglas directamente en PostgreSQL.

Ejemplos:

- No se permite precio negativo.
- No se permite stock negativo.
- No se permite stock_minimo negativo.
- No se permite cantidad de carrito <= 0.
- No se permite cantidad de detalle <= 0.
- No se permite precio historico negativo.
- El total de una orden debe ser exactamente:
  subtotal_antes_de_envio + costo_envio.
- estado_de_pagado solo puede ser APROBADO o DENEGADO.
- estado_envio solo puede estar entre 1 y 5.
- email es unico.
- SKU es unico.
- nombre de categoria es unico.
- nombre de courier es unico.
- nombre de tarjeta es unico.
- No se puede repetir la combinacion:
  producto + talla + color.
- No se puede repetir la misma variante dentro del mismo carrito.
- No se puede repetir la misma variante dentro del mismo detalle de orden.

Las claves foraneas garantizan que no se creen relaciones con registros que
no existan.

18. CONSULTAS ACTUALES DEL BACKEND SOBRE LA BASE
------------------------------------------------

El modulo catalogService usa actualmente:

categoria
producto
variante_producto

Para productos, el backend:
- une producto con categoria mediante INNER JOIN.
- une variantes activas mediante LEFT JOIN.
- agrupa las variantes con JSON_AGG.
- crea cada variante con JSON_BUILD_OBJECT.
- usa COALESCE para devolver [] cuando no hay variantes.
- filtra productos activos.
- puede filtrar por categoria.
- puede buscar un producto por ID.

Esto permite que PostgreSQL devuelva una estructura cercana a:

{
    "id": 1,
    "nombre": "Camiseta Running Pro",
    "precio": 249.99,
    "categoria": "hombre",
    "categoriaNombre": "Hombre",
    "variantes": [
        {
            "idVariante": 1,
            "talla": "S",
            "color": "Negro",
            "stock": 8
        }
    ]
}

La estructura luego se envia al frontend como JSON.
